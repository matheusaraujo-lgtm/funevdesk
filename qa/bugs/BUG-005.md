# BUG-005 — Campanha de QA se auto-bloqueava no rate-limit de login + script e2e-smoke.mjs desatualizado

STATUS: ENVIRONMENT + TEST_BUG (dois problemas distintos, ambos na infraestrutura de teste — nenhum na aplicação)
SEVERITY: N/A
FOUND_BY: Agent 12 (Regression) — 1ª execução completa de `qa/scripts/smoke.mjs`
FOUND_AT: 2026-08-19

## Parte 1 — Rate-limit (ENVIRONMENT)

### Observado
Rodar `discover.mjs`, `permissions.mjs` (2x), `chaos.mjs` (2x), `security.mjs` (2x) e o script de verificação ao vivo de permissões, todos em poucos minutos, cada um autenticando os 3 perfis do zero, ultrapassou o limite de `login:ip:127.0.0.1` (20 tentativas / 5 min, `src/app/api/auth/login/route.js:18`). `e2e-smoke.mjs` (login com senha errada, que deveria dar 401) recebeu 429; `e2e-phase3.mjs`/`e2e-roadmap.mjs` travaram com um `TypeError` não tratado (acessam `dash.currentUser.branchId` sem checar se o login deu certo) e saíram com código de crash do Node; `test-profiles.mjs` falhou em cascata a partir do primeiro login.

### Isto NÃO é um bug do FunevDesk
O rate-limit está funcionando exatamente como projetado — é a própria campanha de QA que precisa respeitar esse limite, não o contrário.

### Correção aplicada na infraestrutura de QA
`qa/scripts/lib/http.mjs:loginAs()` agora tenta de novo com espera de 20s (até 3 vezes) quando recebe 429, em vez de falhar imediatamente. Também documentado aqui para quem for rodar `qa:full` manualmente: **evite rodar vários scripts de QA em sequência muito rápida contra o mesmo servidor** — cada um faz vários logins.

### Recomendação (fora do escopo desta sessão, para o time de produto)
`scripts/e2e-phase3.mjs` e `scripts/e2e-roadmap.mjs` deveriam checar `login(...).cookie` antes de seguir em frente (mesmo padrão de `check(...)` que `e2e-smoke.mjs` já usa), em vez de deixar um `TypeError` não tratado derrubar o processo inteiro sem nenhuma saída útil.

## Parte 2 — `scripts/e2e-smoke.mjs` não preenchia campo customizado obrigatório (TEST_BUG)

### Observado
O tipo de chamado "Problema no computador" (primeiro tipo ativo na organização seed) tem um campo customizado `Sintoma` (SELECT, obrigatório) — provavelmente configurado em algum momento desta sessão de desenvolvimento, depois que `e2e-smoke.mjs` foi escrito. O script monta a criação de chamado só com `title`+`description`, sem `answers`, então a API corretamente rejeita com 400 `{"error":"O campo \"Sintoma\" é obrigatório."}`.

### Isto NÃO é um bug do FunevDesk
A API está corretamente aplicando a validação de campo obrigatório configurada no tipo de chamado.

### Correção aplicada
`scripts/e2e-smoke.mjs` agora monta `answers` a partir de `type.fields.filter(f => f.required)`, escolhendo a 1ª opção quando o campo é `SELECT`. Ver diff em `scripts/e2e-smoke.mjs` (linhas em torno da criação de chamado).

## Reprodutibilidade
Ambos confirmados 100% (rate-limit: reproduzido em toda execução em sequência rápida; campo obrigatório: reproduzido 3 de 3 tentativas antes da correção). Após corrigir os dois e reiniciar o servidor (zera o rate-limit em memória), `qa/scripts/smoke.mjs` foi reexecutado — ver `qa/reports/smoke-summary.md` para o resultado limpo.
