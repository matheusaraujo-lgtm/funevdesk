# BUG-002 — 6 dos 28 módulos de permissão não têm enforcement real no backend

STATUS: FIXED_VERIFIED
SEVERITY: HIGH
FOUND_BY: Agent 7 (Permission Attacker) — varredura sistemática de `can(request, "<module>", ...)` / `requirePermission(...)` em `src/app/api/**` cruzada com `src/lib/permissions.js:MODULES`
FOUND_AT: 2026-08-19
FIXED_AT: 2026-08-20 — `problems`, `changes`, `security`, `audit`, `settings` migrados para `requirePermission(request, "<module>", ...)`; `printers` ganhou checagem em `GET /api/printers/alerts` e `/api/network` agora aceita `network:read` OU `printers:read`.
CONFIRMED_LIVE: sim — ver `qa/scripts/regression-audit-permission-gap.mjs` (caso `audit`, reexecutado após a correção: 200 em vez de 403)

## Esperado
`src/lib/permissions.js` anuncia 28 módulos de permissão, todos configuráveis por perfil em Configurações → Perfis, com a expectativa (reforçada pela UI, que mostra checkboxes independentes para cada um) de que marcar/desmarcar qualquer um deles muda o acesso real àquele recurso.

## Observado
Uma varredura de `grep -rn "\"<module>\"" src/app/api | grep -c "can(\|requirePermission("` para os 28 módulos mostra **6 com zero ocorrências** de enforcement pela própria chave do módulo:

| Módulo (catálogo) | O que a API realmente checa | Arquivo:linha |
|---|---|---|
| `problems` | flag grosseira `canManageTickets` (= `tickets:update`) | `src/app/api/problems/route.js:34,44` |
| `changes` | flag grosseira `canManageTickets` (= `tickets:update`) | `src/app/api/changes/route.js:38,48` |
| `security` | flag grosseira `canViewAssets` (= `assets:read`) | `src/app/api/security/route.js:21` (`canViewAssets` definido em `src/lib/auth.js:124` como `can(user, "assets", "read")`) |
| `printers` | **nada** — `GET /api/network` (fonte real dos dados de impressora) checa só `network:read`; `GET /api/printers/alerts` checa só `requireCurrentUser` (qualquer autenticado, nenhuma permissão) | `src/app/api/network/route.js:56`, `src/app/api/printers/alerts/route.js:11-17` |
| `audit` | hardcoded `auth.user.role !== "ADMIN"` | `src/app/api/audit/route.js:32` |
| `settings` | hardcoded `currentUser.role !== "ADMIN"` | `src/app/api/settings/route.js:49,94` |

Confirmado ao vivo (não só leitura de código): criei um perfil customizado com `baseRole: "TECHNICIAN"` e `audit: { read: true }` explicitamente concedido via `POST /api/profiles`, criei um usuário nesse perfil, logei como ele e chamei `GET /api/audit` → **403 "Acesso restrito."**, mesmo com a permissão granular concedida. Script: `qa/scripts/regression-audit-permission-gap.mjs` (limpa os dados de teste ao final).

## Consequência prática
- Um administrador que cria um perfil "Auditor" (técnico com acesso só a Auditoria, por exemplo) **não consegue** dar esse acesso — o toggle "Auditoria: Ver" no perfil não faz nada.
- Um administrador que tenta restringir "Segurança"/"Problemas"/"Mudanças" para um perfil específico sem também mexer em `assets`/`tickets` **falha silenciosamente** — a UI mostra o toggle desmarcado, mas o acesso real continua vinculado ao módulo errado.
- `GET /api/printers/alerts` é o caso mais grave: **nenhuma permissão de nenhum módulo é checada** — qualquer usuário autenticado, inclusive `EMPLOYEE` (portal do colaborador), consegue ler a configuração organizacional de quais eventos de impressora abrem chamado automático.

## Passos para reproduzir (audit, o mais fácil de confirmar)
1. Como admin: `POST /api/profiles` com `baseRole: "TECHNICIAN"`, `permissions: { audit: { read: true }, tickets: { read: true } }`.
2. `POST /api/users` vinculando um novo usuário a esse `profileId`.
3. Login como esse usuário.
4. `GET /api/audit` → esperado 200 (permissão concedida), observado 403.

## Causa provável
Cada um dos 6 endpoints foi escrito usando o helper de permissão "coarse" (`getPermissions(user).canX`, derivado de `role`) que existia **antes** do sistema de matriz granular por perfil ser introduzido, e nunca foi migrado para `requirePermission(request, "<module>", "<action>")` como o resto das ~60 rotas já faz (confirmado pelo padrão consistente nos outros 22 módulos, todos com `can(`/`requirePermission(` citando a própria chave).

## Recomendação
Migrar os 6 endpoints para `requirePermission(request, "problems"|"changes"|"security"|"printers"|"audit"|"settings", "read"|...)`, e decidir explicitamente o caso de `printers` (ou ganha enforcement próprio, ou é removido do catálogo e o item de menu passa a depender de `network:read` — ver también BUG original sobre este módulo). Enquanto isso não for feito, os checkboxes desses 6 módulos na tela de Perfis deveriam ficar desabilitados com uma nota "ainda não aplicado", para não passar uma falsa sensação de controle ao administrador.

## Reprodutibilidade
5 de 6 casos confirmados por leitura direta de código (determinístico, não depende de estado). 1 de 6 (`audit`) confirmado adicionalmente por execução HTTP real, 1 de 1 execução. Recomenda-se repetir a mesma verificação ao vivo para os outros 5 antes de fechar o item (script generalizável a partir de `qa/scripts/regression-audit-permission-gap.mjs`).
