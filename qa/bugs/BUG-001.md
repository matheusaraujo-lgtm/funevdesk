# BUG-001 — Login de tecnico@local falhava com a senha documentada do seed

STATUS: ENVIRONMENT (resolvido — não é bug da aplicação)
SEVERITY: N/A
FOUND_BY: Agent 2 (System Explorer) / Agent 11 (Bug Investigator)
FOUND_AT: 2026-08-19

## Esperado
Login com `tecnico@local` / `Tecnico@123` (credenciais documentadas em `scripts/seed-demo.cjs` e reaproveitadas por `qa/config/users.json`) deveria retornar 200.

## Observado
`POST /api/auth/login` retornava 401 `{"error":"E-mail ou senha inválidos."}` tanto via UI quanto via API direta. A conta existe e está ativa (`GET /api/users` confirmou `active: true`, role `TECHNICIAN`).

## Passos para reproduzir (antes da correção)
1. `POST /api/auth/login` com `{ "email": "tecnico@local", "password": "Tecnico@123" }`.
2. Resposta: 401.

## Evidência
- `qa/scripts/_debug-login.mjs` (screenshot `qa/evidence/_debug-tecnico.png`) mostrou a tela de login exibindo "E-mail ou senha inválidos."
- Teste via API direta confirmou o mesmo 401, eliminando causa na camada de UI.
- `GET /api/users` como admin confirmou a conta existe e está ativa — eliminou hipótese de conta ausente/desativada.

## Causa provável
Divergência entre a senha atualmente hasheada no banco de desenvolvimento e o valor documentado em `scripts/seed-demo.cjs:28` (`PASSWORDS.tech = "Tecnico@123"`). `seed-demo.cjs` é idempotente e reescreve o hash a cada execução (`upsertUser` → `UPDATE users SET password_hash=?`), mas não havia sido reexecutado desde alguma alteração manual da senha (ex.: troca de senha durante testes manuais anteriores nesta sessão de desenvolvimento). Não é falha do código da aplicação — é o dado local ter divergido do fixture documentado.

## Resolução
`npm run seed:demo` (script confirmado sem `DELETE`/`DROP`/`TRUNCATE` — só upsert por e-mail, seguro para reexecutar). Após a reexecução, login via API confirmado com 200.

## Reprodutibilidade
3 de 3 tentativas falhavam antes da correção; 1 de 1 tentativa passou depois.

## Recomendação
`qa/scripts/run-full.mjs` deve rodar `npm run seed:demo` como pré-requisito automático de toda campanha (implementado — ver seção "Pré-voo" do script), para este tipo de divergência nunca mais bloquear uma campanha inteira silenciosamente.
