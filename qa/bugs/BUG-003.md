# BUG-003 — `users:read` bypassado por flag grosseira; `categories` sem checagem alguma

STATUS: PARTIALLY_FIXED (users corrigido; categories deixado como está, ver nota)
SEVERITY: MEDIUM
FOUND_BY: Agent 7 (Permission Attacker) — `qa/scripts/permissions.mjs`, execução real
FOUND_AT: 2026-08-19
FIXED_AT: 2026-08-20 — `src/app/api/users/route.js` GET agora também aceita `can(user,"users","read")` além das flags grosseiras existentes (aditivo, não removeu o comportamento anterior). `categories` NÃO foi alterado nesta rodada — risco de quebrar filtros do portal do usuário (EMPLOYEE) sem confirmar todos os consumidores primeiro; fica registrado para revisão dedicada.

## Parte 1 — `GET /api/users` ignora `users:read`

### Esperado
Perfil "Técnico" (seed) tem `users: ""` (nenhuma letra concedida) em `src/lib/permissions.js:SEED_PROFILES` → `users:read` deveria ser `false`.

### Observado
`GET /api/users` autenticado como `tecnico@local` retornou 200 com a lista completa de usuários da organização (nome, e-mail, role, unidades). Código (`src/app/api/users/route.js:162`): `if (!permissions.canConfigure && !permissions.canManageTickets) return 403`. Como o perfil Técnico tem `tickets: "rcud"` (→ `canManageTickets=true`), a checagem de `users:read` nunca é avaliada.

### Diferença em relação às exceções legítimas (`locations`/`term_templates`)
Aquelas duas têm uma checagem OR que **inclui** a própria permissão do módulo (`can(user,"locations","read") || ...`) — ou seja, desmarcar as duas permissões-fallback ainda bloqueia se `locations:read` for concedido, e o dado exposto é de baixa sensibilidade (nomes de sala/prédio). Aqui, `users:read` **nunca entra na conta** — não existe combinação de permissões em que desmarcar as duas flags grosseiras e marcar só `users:read` funcione, e o dado exposto (e-mail, role, vínculo de unidade de TODOS os usuários da organização) é mais sensível.

### Passos para reproduzir
1. Login como `tecnico@local` (perfil seed "Técnico", `users` sem nenhuma letra concedida).
2. `GET /api/users` → 200 com a lista completa (confirmado em `qa/evidence/permissions-*.json`).

### Causa provável
`src/app/api/users/route.js:162` usa `canConfigure || canManageTickets` em vez de `can(currentUser, "users", "read")`. Provavelmente intencional para permitir que técnicos vejam nomes de colegas ao atribuir chamados — mas o endpoint devolve a lista INTEIRA (não uma versão reduzida "apenas nome" para dropdown de atribuição), então a intenção razoável ("ver quem pode ser responsável") acaba concedendo acesso a mais dado do que o necessário.

### Recomendação
Se a intenção é só alimentar um seletor de responsável, criar um endpoint reduzido (`GET /api/users/assignable` retornando só `id`+`name`) e restringir `GET /api/users` (completo) a `can(user, "users", "read")` de verdade.

## Parte 2 — `GET /api/categories` sem checagem de permissão alguma

### Esperado
Perfis sem `categories:read` (Técnico e Usuário, ambos `""` no seed) deveriam receber 403.

### Observado
`GET /api/categories` (`src/app/api/categories/route.js:12-14`) só chama `requireCurrentUser` — sem `can()`/`requirePermission()` depois disso. Qualquer autenticado, inclusive `EMPLOYEE`, lê a lista de categorias.

### Severidade
Baixa em isolamento (dado é só rótulo + cor de categoria, sem PII) — mas listado aqui porque, diferente de `statuses`/`ticket_types` (que têm justificativa clara: todo usuário PRECISA ler status/tipo pra usar o sistema), não há nenhum comentário no código explicando a decisão, sugerindo que pode ser um descuido, não uma escolha deliberada.

### Recomendação
Se for intencional (provável, já que categorias aparecem em filtros do portal do usuário), adicionar um comentário como em `locations`/`term_templates` para deixar explícito — evita que uma futura correção "quebre" sem entender o motivo original.

## Reprodutibilidade
Ambos confirmados por execução real de `qa/scripts/permissions.mjs` (não é amostra — é a matriz completa rodada contra os 3 perfis seed).
